# 9. Shutdown & Process Cleanup

Close retains the shared daemon; Restart stops what this generation owns, then re-execs; Panic stops everything before any cleanup. A signal never proves an exit: a stop requires confirmed death; unconfirmed custody remains for the next start to retry.

### Shutdown doors

| Door | Stops | Keeps | Durable mark |
|---|---|---|---|
| Window close with keep-running on (desktop, live indicator) | nothing: the window hides | every task, schedule, companion and the daemon | none |
| Close, quit, SIGTERM | this generation's workers, services and owned executor/task processes | the shared daemon and its clients; saved pauses | `server_shutdown.cause`: `external_signal` or `launcher_quit` |
| Planned restart (self-restart, update, rollback) | the same; the daemon only when the landed checkout pins another engine | saved pauses; a same-pin daemon | the restart handoff |
| Manual Restart (owner) | the same plus the installation daemon and every delegated run it serves, other clients' included | saved pauses; never-started rows, held | `owner_restart_no_resume.flag` |
| Panic | all owned work; the daemon by confirmed ledger identity | nothing resumes until the owner acts | `panic_stop.flag` |

**Close, quit, Panic (desktop).** `launcher_background.py` decides a window close from `OUROBOROS_DESKTOP_KEEP_RUNNING`, read at that moment: on, with a live indicator (Windows, macOS), the window hides; off, or without an indicator, the close quits through the teardown below; undecided, the first close asks once and stores the answer. A quit (the indicator's Quit, Cmd+Q, sign-out, shutdown) is never asked or cancelled and sets no Panic flag. Panic keeps its own path: the server exits with the Panic code, the lifecycle thread asks the indicator to go without waiting for it, and the indicator's Panic item posts `/api/command /panic` over loopback, as Android's notification does. A second manual launch shows the running window, even while that copy still boots; Linux keeps the plain close.

Close stops this generation's workers and services and releases its PID lock; the daemon stays because it serves work beyond one window (Windows keeps it outside the launcher Job; spawn custody and the reaper: §1 Runtime topology). `launcher.stop_agent` signals the server PID only (POSIX SIGTERM; Windows `quit\n` on the owned stdin, `OUROBOROS_LAUNCHER_STOP_STDIN`), waits `LAUNCHER_STOP_GRACE_SEC`, then forces group/Job cleanup; the signal sets the stop latches at once and `SERVER_GRACEFUL_SHUTDOWN_TIMEOUT_SEC` bounds the Uvicorn drain, so custody completes even when the whole group is signalled. `_exit_signalled` is never cleared, so a settings save landing mid-teardown cannot revive a supervisor generation; `_supervisor_stop` is cleared by a fresh lifespan (`server.py`).

### Restart and retention

Teardown sets the stop flag, joins the supervisor within its bound and terminalizes `kill_workers` before optional waits and sweeps; the restart watcher owns final cleanup and the handoff. Owned processes stop once (`owned_shutdown.stop_owned_work`): the first door starts the grace and stamps every pending stop, later doors join, and what the grace cannot confirm is stamped `unconfirmed_since` for the next start to retry before admission (§10 invariant 6). A planned restart keeps a same-pin daemon and ends it only for a new engine pin (`server_restart._stop_owned_daemon_for_new_pin`); a restart carrying a body adoption arms it only on the stop owners' own evidence (§6 Own-body candidates). POSIX re-execs in place; Windows, whose C runtime only emulates exec, spawns the custodied successor and exits 42, so there the handoff token is no recovery acknowledgement: proof still needs the same PID. Restart runs no port sweep: exec closes its own listeners and a port is no ownership proof; the launcher, recovery and Panic sweeps stay separate and may stop unrelated listeners.

Manual Restart (`server_restart._perform_owner_restart`) refuses before anything stops: the update lock, the managed-update transaction and `safe_restart` run first, and a refusal, an unwritable no-resume flag included, reports "Restart cancelled" with the server intact. Past that gate it proceeds despite unconfirmed cleanup: write `owner_restart_no_resume.flag` (an existing Panic flag is preserved), request `owner_restart` cancellation for live work except saved pauses, `kill_workers(hold_never_started=True)`, `reconcile_orphaned_runs` through the attach-only `read_owned_gateway`, the daemon's `stop_outcome`, then the owned stop; no step may call `ensure_owned_gateway`, which would start a dead daemon. An unconfirmed step is a critical diagnostic (`process_stop_unconfirmed`) with custody retained, never a veto. At boot `owner_restart` is one of `delegate_recovery.NO_RESUME_CAUSES`: nothing is adopted, and owner-gone runs settle from their own evidence (`close_absent_run` for an absent run, the journal for a terminal one) without invented spend.

**Retention.** Every stop keeps a saved pause saved (`restart_retention.py`, restored by `queue_snapshot.py`): signal first, park the marker, never terminalize or emit `task_done`; an unused Resume grant returns to Pause; post-task remainders stay in `root_phase_checkpoint` with no auto-resume (§6). Manual Restart also holds never-started rows (`admitted_dispatch=none`, interrupted parents' children included) under `reason_code=owner_restart_hold`; a row whose dispatch evidence is missing stays held as `dispatch_outcome_unknown` rather than being called never started; only selectable holds release through explicit Resume or model selection under a live root grant; unknown dispatch needs reconciliation; Stop cancels, and the Restart notice reports the held count. Explicit Stop wins over any pause; `pausing` without a stored source is interrupted intent: Continue, not exact Resume. Panic needs no prerequisite from any of this.

### Panic path

Panic requests owned stops before any I/O or cleanup and never waits on nonessential work (BIBLE Emergency Stop Invariant). The worker socket gives local owners a short window, the lifeline bounds its callback, and the parent requests the worker kill from its own Popen on its own timer whatever the lifeline did. Delivery, signal request and proven death stay three facts: unpublished spawns, inaccessible owners and backend-only children remain unconfirmed. Live WS/HTTP Panic reaches the emergency owner through `LocalChatBridge.panic` without waiting for supervisor intake or state I/O; Host Service ingress authenticates the skill and matches the pinned owner pair (§12). Boot consumes the flag only after the disabled controls persist; a persistence failure retains it and also aborts reviews of newly admitted owner work until a subsequent Restart can persist the controls.

### Owned daemon stop and startup failure

`OwnedClaudexorDaemon.stop_outcome` (Panic and Restart) returns `stopped`, `nothing_to_stop` or a disclosed `unconfirmed`. Cooperative first: with a valid owned marker and an authenticated same-home endpoint it runs the installed CLI `daemon stop --json` and requires exit 0 plus the typed terminal receipt, because an RPC acknowledgement or a lease release does not prove the OS processes exited; forced signalling then covers only the pre-request custody snapshot and needs measured birth and command identity or the manager's own Popen. Only confirmed death removes custody; a token refusal, invalid discovery or a matching error string grants no stop authority. Lock, RPC and exit waits are bounded separately by `CLAUDEXOR_OPERATOR_STOP_TIMEOUT_SEC` and `CLAUDEXOR_STOP_EXIT_WAIT_SEC` (§7), with no promised total. A live startup outlives its caller's `CLAUDEXOR_STARTUP_WAIT_SEC` window: `daemon_starting` invites joining it, `daemon_spawn_failed` names an exited child. The rules a change must keep: DEVELOPMENT "Process Custody Rule".

**Startup failure.** `claudexor_startup_failure.py` labels an owned child's exit without a control endpoint, from its own `daemon.log` interval, as `heap_exhausted`, `writer_lease_contended`, `engine_floor` or `unclassified`; the label is diagnostic, never behavior, carried in the typed `daemon_spawn_failed` detail, `last_error` and one durable `claudexor_daemon_start_failed` row. The latch keys on the typed exit alone. While it is set, every ordinary caller gets an immediate `daemon_spawn_failed` without a spawn, unless a live startup exists, which it joins. Each manager has its own latch, released by a live-daemon attach or a new manager. The server's latch also releases through the periodic custody sweep (§5), which makes one zero-wait ensure only when it released a latch, or the owner's Refresh (`/api/claudexor/wake`), one spawn per press; a worker's latch needs an attach or worker respawn. Attach, sweep and Refresh releases are rowed as `claudexor_daemon_start_latch_cleared` with `cleared_by`. The host adds no backoff, cooldown or writer-lease handling. The host derives no heap size from RAM, which only moves the crash; the engine names its own ceiling through probe `launch.nodeArgs` and managed launch passes it as a bounded `--max-old-space-size`. An explicit `NODE_OPTIONS` heap option wins, as the operator's escape hatch; missing or malformed launch data keeps the plain command (`runtime_launch_invalid` in runtime diagnostics). Harvest cadence: DEVELOPMENT "Process Custody Rule"; the two disclosed latch residuals: `claudexor_startup_failure.ExitFact` and `OwnedClaudexorDaemon.clear_start_failure_latch`.

`claudexor_exit_facts.py` reads the engine's recent exits (phase, class, signal or code, pin; the host's observation time, not the death time) from the bounded tail of `supervisor.jsonl` for context, which never calls the engine. The owned-daemon status read (`/api/claudexor/status`, §4) adds `last_exit` and live `memory` from the already-running endpoint, null when unknown or the engine is old, and records one `claudexor_engine_capacity` row per descriptor generation. These are observations, not lifecycle authority: no heap threshold, notification or restart policy follows.

### Process custody

`_active_subprocesses`, task-attributed executor records (§1) and ledgered task processes are named by `state/owned_processes.json` (a contended registration lands in `owned_processes.pending/`), which exit and Panic read instead of walking `data/state`; a boot side thread indexes older records once. Groups and Jobs miss escaped descendants, so a signal needs the measured identity, and startup recovery settles no executor backend: only stamped stops are retried. Docker CLI exit proves no backend exit: `backend_completed` is persisted before marker deletion, and a lost reply retains evidence rather than signalling a completed CLI PID. Host unwind or exact worker death retires the local invocation only (§6); unknown effects never authorize replay.

**Follow-up controls.** An accepted Stop transfers its control identity to the original task result before the active intent retires, also when natural completion wins, so the completed status and result survive; a failed transfer keeps the intent for recovery. A recorded cancel intent wins over the door's cause; an unreadable store invents none. Manual Restart keeps its control in the schedule document before consuming its marker; Panic needs none. Owner: `supervisor/followup_policy.py`.

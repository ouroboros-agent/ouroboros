# MCP Client Integration

This chapter owns the boundary for configured MCP servers: the runtime is a client, never a server; remote data is not policy; only the owner selects Settings references. It also fixes how a referenced settings value reaches a process environment, because the value's secret classification decides whether it is masked in diagnostics and logs.

The base runtime is an optional client for trusted HTTP/SSE and local stdio MCP servers, never an MCP server (structure, transport validation, the stdio `command`/`args`/`cwd`/`env`/`env_from_settings` contract, server identity, catalog lookup and the masking rule: ARCHITECTURE §6 "MCP and browser-facing external tools"; `ouroboros/mcp_client.py`). MCP descriptions and results are untrusted data: configuration trust must not turn remote prose into policy. Enabled tools join the initial capability envelope and still pass runtime safety and the caller's ordinary capability ceiling; a discovery failure is a visible capability omission. The owner selects MCP references in Settings; a caller's existing MCP tool grant does not authorize new references. Executable schema properties, required fields, enum and default values stay intact, and wire tool names stay unchanged. Resources, prompts and MCP server behaviour are separate architecture changes. Enforcement: `tests/test_mcp_client.py`, `tests/test_mcp_server_identity.py`.

`start_service` overlays literal `env` on its minimal host baseline; commands, scripts and run-kind verification keep their inherited environment. Resolve Settings references once after admission through `workspace_executor.resolve_process_env` (mechanism: ARCHITECTURE §6 "Safety and runtime mode"). Keep `env_from_settings` behind the host-owned `ouroboros/tools/process_facts.py::settings_environment_allowed` authority, which admits root and Cyber acting tasks and excludes Presence; configured MCP access and skill grants do not expand that authority or authorize an unrelated service. A referenced field keeps its secret or ordinary classification: a secret is masked in service diagnostics and finalized log blobs, and never enters host argv, generated shell source or the durable process ledger; Docker forwards it through inert CLI environment aliases. Enforcement: `tests/test_process_environment.py`, `tests/test_workspace_executor_services.py`.
